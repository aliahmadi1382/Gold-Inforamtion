# تحویل ۰٫۱۵ — پشتیبان سازگار و بازیابی آزمایشی

تاریخ: ۸ اکتبر ۲۰۲۶. دامنهٔ این تحویل، حفاظت و بازیابی **داده‌های اصلی store** و هماهنگی نویسنده‌های پروژه است؛ تکمیل همهٔ عملیات، زمان‌بندی یا دریافت تازهٔ بازار نیست.

## دامنهٔ بسته

`backup-store` یک پوشهٔ تازه شامل `market.sqlite3`، همهٔ فایل‌های محتوامحور `raw/` و اسناد JSON `runs/` می‌سازد. خام‌های بدون رکورد نیز حفظ می‌شوند؛ ممکن است شاهد metadata یا تلاش ناموفق باشند. فقط خام‌های مستقیم رکوردها کافی نیستند، زیرا زنجیرهٔ COT و رسید دریافت فایل‌های دیگر هم دارد.

فایل کلید، `.env`، گزارش‌های جانبی داخل store، کد، تنظیمات، گزارش‌های بیرون از store و فایل‌های lock/WAL/SHM در این بسته نیستند. بقایای غیر JSON نوشتن اتمیک یا رزرو در runs نیز سند دریافت نهایی محسوب نمی‌شوند. پوشه‌های `local/reports` و `local/integration-*` و نسخهٔ متناظر کد/config را جدا حفظ کنید؛ کلید از مسیر امن مالک بازتنظیم شود. دادهٔ اصلی و پشتیبان خصوصی‌اند و وارد مخزن عمومی نمی‌شوند.

## سازگاری و قفل

SQLite Online Backup API، صفحات **commitشدهٔ WAL** را در پایگاه مقصد می‌آورد؛ کپی مستقیم فایل اصلی باز ممکن است آن‌ها را از دست بدهد. پایگاه مقصد پس از backup به journal mode DELETE تبدیل و اتصال بسته می‌شود؛ سپس اندازه و هش آن محاسبه می‌شود. انتظار SQLite محدود است: اتصال پنج ثانیه و callback پشتیبان حداکثر حدود سی ثانیه، با امکان شکست روشن در رقابت خارجی.

`writer.lock` یک قفل غیرمنتظر سیستم‌عامل است که پشتیبان و نویسنده‌های پروژه مشترک دارند. `Store` هنگام راه‌اندازی، `put_raw` و `put` قفل می‌گیرد؛ `acquire` از پیش از رزرو/سند آغاز تا سند پایان و `refresh-report` تمام گردش را پوشش می‌دهند. فراخوانی‌های تو‌در‌تو در همان Store و thread قفل خود را استفاده می‌کنند؛ thread دیگر اجازهٔ استفاده از مالکیت آن را ندارد. فایل باقی‌مانده، قفل فعال نیست و نباید برای دورزدن آن حذف شود. خاتمهٔ فرایند قفل OS را آزاد می‌کند.

قفل قدیمی `refresh.lock` برای سازگاری باقی است. هم‌اکنون دریافت‌های مستقل، refresh و backup روی یک store با هم رقابت می‌کنند؛ بازکردن یک Store تازه نیز می‌تواند در این مدت رد شود. خطا انتظار نامحدود یا retry خودکار ایجاد نمی‌کند.

این قفل SQL دستی روی `store.db`، ابزار خارجی SQLite یا دست‌کاری فایل‌ها توسط برنامهٔ دیگر را کنترل نمی‌کند. برای این ابزارها، عملیات نوشتن را متوقف کنید. برنامه تغییر مجموعه/هش خام‌ها و اسناد هنگام کپی را نیز می‌سنجد و نسخهٔ مخلوط را موفق اعلام نمی‌کند؛ این سنجش جای پروتکل مشترک را نمی‌گیرد.

## کنترل‌ها و قرارداد

`BackupManifest` نسخهٔ ۱، زمان، نسخهٔ کد، مسیر منبع، scope، فهرست مسیر/اندازه/هش، تعداد نسخه‌های رکورد، تمام raw و سندها و تعداد وضعیت‌های running/succeeded/failed را ثبت می‌کند. `RestoreReceipt` نسخهٔ ۱، fingerprint پشتیبان، مسیر store بازیابی‌شده و نتیجهٔ بررسی را ثبت می‌کند. قراردادهای داده/گزارش/refresh قبلی تغییر نکرده‌اند؛ تعداد Schemaها ۳۸ است.

پیش از انتشار و در `verify-backup`، integrity پایگاه، قرارداد و هش محتوا برای هر رکورد، وجود خام مستقیم، هش تمام raw و اتصال `raw_sha256`/`record_ids` هر سند دریافت کنترل می‌شود. نام خام باید SHA-256 محتوا باشد و نام سند با run_id تطبیق داشته باشد. مسیر فراری، فایل/دایرکتوری symlink و اسناد ناسازگار رد می‌شوند. شمارش و متن فارسی از manifest دوباره بررسی می‌شوند. هش مجدد یک پایگاه با رکورد دست‌کاری‌شده یا شمارش جعلی، کنترل معنایی را دور نمی‌زند.

اسناد failed و running با وضعیت اصلی حفظ می‌شوند؛ پشتیبان‌گیری آن‌ها را موفق یا کامل نمی‌کند. تعداد record، نسخهٔ ذخیره‌شده است، نه تعداد مشاهدات اقتصادی یکتا. این کنترل اصالت ناشر، دقت اقتصادی یا سودآوری را ثابت نمی‌کند.

## اجرا و رفتار شکست

```powershell
uv run gold --store local/market backup-store --output-dir local/backups
uv run gold verify-backup PATH_TO_BACKUP
uv run gold restore-store PATH_TO_BACKUP --destination local/restore-tests/NEW_NAME
uv run gold --store local/restore-tests/NEW_NAME/store audit
```

دستورها شبکه، registry یا کلید لازم ندارند. source اشتباه، store خالی خودکار ایجاد نمی‌کند؛ store خالی **موجود و معتبر** قابل پشتیبان‌گیری است. خروجی backup باید بیرون از source باشد. هر اجرا نام تازه دارد و نسخهٔ قبلی بازنویسی نمی‌شود.

مقصد restore یک **container تازه و ناموجود** است؛ store پس از بررسی در زیرپوشهٔ `store/` منتشر و رسید کنار آن نوشته می‌شود. مقصد موجود حتی اگر خالی باشد، داخل backup یا داخل source اصلی رد می‌شود. برنامه پوشهٔ مقصد را انحصاری رزرو می‌کند و فایل‌ها را ابتدا در `.incomplete-store` می‌نویسد. خطا می‌تواند این container ناتمام را باقی بگذارد؛ موفقیت چاپ نمی‌شود و اجرای مجدد باید مقصد تازه داشته باشد. پایگاه فعلی حذف یا جایگزین نمی‌شود.

backup نیز ابتدا در `.incomplete-backup-*` ساخته و پس از بررسی به نام نهایی منتقل می‌شود. خطای دیسک/کپی/منشأ پوشهٔ ناتمام می‌گذارد، نه پشتیبان موفق. کد صفر فقط پس از بررسی و انتشار/رسید است؛ خطاهای ورودی، قفل، دیسک یا دادهٔ خراب کد ۲ دارند. متن خطای شبکه یا credential به manifest اضافه نمی‌شود.

## نتیجهٔ واقعی محلی

پشتیبان ۸ اکتبر از `local/market` شامل **۸۸٬۷۰۷ نسخه، ۷۹ فایل خام و ۶۵ سند دریافت** است: ۶۰ موفق، ۵ ناموفق و صفر running. این تعداد raw از ۶۰ خام مستقیم بیشتر است؛ خام metadata و تلاش‌های بدون رکورد نیز حفظ شده‌اند. ۱۴۵ فایل اصلی در manifest آمده‌اند.

بسته در `local/backups/v015/` ساخته و در `local/restore-tests/v015-20261008/store` بازیابی شد. تمام ردیف‌های پایگاه منبع/مقصد برابرند و audit هر دو موفق است. گزارش با cutoff و تنظیمات ثبت‌شده، در **کد ۰٫۱۵ و Python 3.12.14 یکسان** از source و restore ساخته شد؛ هر دو fingerprint برابر `0752d6e…` و مقایسه `unchanged` دارند. رسیدها در `local/integration-v015/` نگهداری می‌شوند.

بازتولید گزارش قدیمی ۰٫۱۳ در Python 3.12، ۴۲ اختلاف Pearson متحرک با حداکثر اختلاف مطلق `2.22e-16` نشان داد. روی همان store و lock وابستگی، بازحساب با Python 3.11.16 **صفر تغییر محتوا** و فقط تغییر نسخهٔ نرم‌افزار دارد. تغییر الگوریتم جمع float در ۳٫۱۲ در [مستند رسمی Python](https://docs.python.org/3.12/library/functions.html#sum) آمده است؛ این نتیجهٔ کنترل‌شده، تفاوت دقت runtime را نشان می‌دهد، نه تغییر داده یا خرابی restore. روش عددی در این تحویل دست‌کاری نشده و اختلاف‌ها در comparator پنهان نشده‌اند. برای بازتولید دقیق، نسخهٔ interpreter نیز کنار کد، lock، cutoff و تنظیمات نگهداری شود. رسید مقایسهٔ runtime در `local/integration-v015/runtime-validation.json` است.

این نسخهٔ پشتیبان روی همان دیسک C است؛ آزمون بازیابی محلی را اثبات می‌کند، اما نسخهٔ مستقل در برابر از‌دست‌رفتن آن دیسک نیست. مقصد خارج از دستگاه، نگهداری/حذف دوره‌ای و زمان‌بندی هنوز تنظیم نشده‌اند. مرحلهٔ بعد، سلامت اجراها و سیاست سهمیه/خطا و retry محدود است؛ مشکل دسترسی CFTC و دروازهٔ روش قیمت/انتشار همچنان بازند.
