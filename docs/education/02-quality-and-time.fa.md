# فصل ۲ — چرا دادهٔ زیاد کافی نیست؟

## سه زمان متفاوت

فرض کنید یک گزارش، وضعیت روز سه‌شنبه را اندازه گرفته، جمعه منتشر شده و شما شنبه آن را دریافت کرده‌اید:

| زمان | نام در برنامه | کاربرد |
| --- | --- | --- |
| زمان اندازه‌گیری یا دورهٔ گزارش | observed_at | داده دربارهٔ چه زمانی است؟ |
| اولین زمان مستند دسترسی به همین نسخه | available_at | بازار از چه زمانی می‌توانست این نسخه را بداند؟ |
| زمان دریافت در این سامانه | retrieved_at | سامانهٔ ما چه زمانی آن را دریافت کرد؟ |

استفاده از آن گزارش در تحلیل چهارشنبه، خطای **Look-ahead bias** یا استفاده از اطلاعات آینده است. اگر زمان واقعی انتشار معلوم نباشد، برنامه `available_at` را برابر زمان دریافت قرار می‌دهد. این انتخاب محتاطانه باعث می‌شود تاریخچهٔ تازه‌دانلودشده، خودبه‌خود برای بک‌تست قدیمی معتبر محسوب نشود.

در حالت `system` هر دو زمان دسترسی و دریافت باید قبل از زمان تحلیل باشند. حالت `source` فقط شرط زمان دسترسی را اعمال می‌کند؛ انتخاب این حالت، زمان انتشار نامعلوم را معتبر نمی‌کند.

## اصلاحیه با مشاهدهٔ جدید فرق دارد

اگر مقدار تورم یک ماه بعداً اصلاح شود، دو نسخه برای همان دوره داریم. آن‌ها دو ماه تاریخچه نیستند. گزارش کیفیت، `record_versions` را جدا از `unique_observations` نشان می‌دهد. دو نسخهٔ متفاوت با زمان دسترسی و دریافت یکسان ابهام ایجاد می‌کنند؛ برنامه آن را خطا گزارش می‌کند.

## منشأ و SHA-256

`Provenance` اطلاعات شناسنامهٔ داده و `Lineage` زنجیرهٔ ارتباط خروجی با ورودی است. SHA-256 یک اثر انگشت از بایت‌های فایل می‌سازد. تغییر بایت‌های فایل، اثر انگشت را تغییر می‌دهد. تطابق هش می‌تواند تغییر فایل را آشکار کند؛ **درستی اقتصادی قیمت را اثبات نمی‌کند**. فایل اصلی، روش تبدیل، ارائه‌دهنده و حق استفاده همچنان مهم‌اند.

`Manifest` گزارش یک عملیات دریافت یا ورود است: چه عملیاتی، چه زمانی، با چه پارامترهای غیرمحرمانه‌ای، روی چه فایل‌ها و رکوردهایی انجام شد و آیا موفق بود. اجرای شکست‌خورده نیز ثبت می‌شود. وضعیت `running` بدون زمان پایان ممکن است نشانهٔ قطع فرایند باشد؛ آن را موفق فرض نکنید.

## خواندن گزارش کیفیت

```sh
uv run gold demo
uv run gold --store local/demo quality --as-of 2024-04-22T22:00:00Z --allow-synthetic --output local/demo/quality.json
```

این دستور فقط دادهٔ مصنوعی را می‌سنجد. برای دادهٔ واقعی، `--allow-synthetic` را حذف کنید. `pass` یعنی بررسی‌های تعریف‌شده خطایی ندیده‌اند، نه اینکه مجموعهٔ داده برای سودآوری یا تحلیل تاریخی کامل تأیید شده باشد.

| پیام | معنی و اقدام |
| --- | --- |
| NO_ELIGIBLE_DATA | در زمان انتخاب‌شده هیچ دادهٔ معتبر قابل دسترسی نیست؛ مسیر و زمان‌ها را بررسی کنید |
| SOURCE_MISMATCH | مشخصات یا مجوز داده با رجیستری فرق دارد؛ منبع را بررسی کنید |
| RAW_MISSING / RAW_CORRUPT | فایل اصلی موجود نیست یا تغییر کرده است؛ نسخهٔ معتبر را بازیابی کنید |
| AMBIGUOUS_REVISION | انتخاب نسخهٔ نهایی مبهم است؛ شواهد انتشار و نسخه را بررسی کنید |
| MISSING_VALUES | بعضی مقدارها نامعلوم‌اند؛ صفر جای آن‌ها نگذارید |
| RELEASE_TIME_UNKNOWN | زمان انتشار دقیق معلوم نیست؛ تحلیل قدیمی به شواهد بیشتری نیاز دارد |
| STALE_REFERENCE | جدیدترین زمان مرجع از حد تنظیم‌شده قدیمی‌تر است |
| DAILY_GAP_REVIEW | فاصلهٔ تقویمی بزرگ دیده شده؛ تعطیلی بازار یا قطع داده باید بررسی شود |
| REQUIRED_STREAM_MISSING | هیچ سری مستقل، تعداد مشاهدهٔ لازم را ندارد |

آخر هفته و تعطیلی با خرابی داده یکسان نیست. نسخهٔ فعلی شمارش قطعی روز معاملاتی ازدست‌رفته انجام نمی‌دهد و فقط فاصلهٔ بزرگ را برای بررسی نشان می‌دهد. آستانه‌ها در `config/quality_policy.yaml` قابل مشاهده‌اند. مقادیر سیاست کیفیت، قانون ورود به معامله نیستند.

## تمرین

یک گزارش سه‌شنبه اندازه‌گیری و جمعه منتشر شده است. آیا استفاده از آن برای تصمیم پنجشنبه مجاز است؟ خیر. اگر مقدار مشاهده صفر باشد، آیا داده مفقود است؟ خیر؛ در قرارداد ما مقدار مفقود `null` است. اگر ۵۰ نسخه برای ۱۰ روز داشته باشیم، آیا شرط ۵۰ روز تاریخچه برقرار است؟ خیر.
