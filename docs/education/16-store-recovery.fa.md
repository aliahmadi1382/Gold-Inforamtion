# فصل شانزدهم — پشتیبان‌گیری، WAL و بازیابی

GitHub کد را حفظ می‌کند؛ داده، خام، کلید و گزارش واقعی در `local/` هستند. پس clone تازه به‌تنهایی بازار ثبت‌شدهٔ شما را بازیابی نمی‌کند.

## چرا فقط SQLite کافی نیست؟

هر رکورد به فایل خام و سند دریافت متصل است. پایگاه بدون خام، زنجیرهٔ منشأ را از دست می‌دهد. بعضی خام‌ها metadata یا پاسخ تلاش ناموفق‌اند و هنوز رکورد ندارند؛ برای بازسازی زنجیره، آن‌ها هم در پشتیبان ۰٫۱۵ نگهداری می‌شوند.

SQLite ممکن است تغییرهای commitشده را در **WAL**، فایل جانبی write-ahead log، نگه دارد. کپی مستقیم فایل اصلیِ باز ممکن است این تغییرها را جا بگذارد. API پشتیبان SQLite آن‌ها را به مقصد سازگار می‌آورد؛ آزمایش واقعی WAL در آزمون‌های پروژه وجود دارد.

## قفل چه می‌کند؟

اگر دریافت یا ورود پروژه در حال نوشتن باشد، backup روی همان store رد می‌شود. برعکس، هنگام backup نویسندهٔ دیگر رد می‌شود. این شکست روشن بهتر از اعلام یک بستهٔ ناسازگار است. فایل `writer.lock` پس از اجرا باقی می‌ماند؛ وجود فایل به معنی قفل فعال نیست. حذف آن روش آزادکردن قفل نیست؛ OS با پایان فرایند مالکیت را آزاد می‌کند.

ابزار خارجی SQLite و تغییر دستی فایل‌ها باید جدا متوقف شوند؛ از قفل برنامه پیروی نمی‌کنند.

## سه مرحلهٔ عملی

```powershell
uv run gold backup-store --output-dir local/backups
uv run gold verify-backup PATH_TO_BACKUP
uv run gold restore-store PATH_TO_BACKUP --destination local/restore-tests/NEW_NAME
```

اولی snapshot و manifest می‌سازد. دومی فایل‌ها، پایگاه، قرارداد رکورد و اتصال به خام/سند را بررسی می‌کند. سومی در container تازه، زیرپوشهٔ `store` را بازیابی می‌کند. مقصد موجود بازنویسی نمی‌شود؛ مسیر store از خروجی CLI خوانده می‌شود.

برای آزمون بازیابی، audit کافی نیست: یک گزارش با همان cutoff، تنظیمات، registry، نسخهٔ کد **و Python** روی source و restore بسازید و نتیجه را مقایسه کنید. تغییر کد یا runtime می‌تواند fingerprint را عوض کند، حتی وقتی تمام ردیف‌ها یکسان‌اند. در بررسی واقعی این تحویل، Python ۳٫۱۲ ضرایب Pearson را در حد `2.22e-16` متفاوت بازحساب کرد؛ با Python ۳٫۱۱ محتوای گزارش قدیمی دقیقاً تکرار شد. این اختلاف، حرکت بازار نیست؛ جزئیات در [روش تحویل](../source-methodology/store-recovery.fa.md) آمده است.

## چه چیزهایی جدا می‌مانند؟

پشتیبان اصلی، کلید و گزارش‌های بیرون از store را شامل نمی‌شود. کد/config را در نسخهٔ مناسب Git نگه دارید؛ گزارش‌ها و رسیدها را جدا حفظ کنید و کلید را از مسیر امن خودتان تنظیم کنید. پشتیبان واقعی و دادهٔ مشتق‌شده وارد مخزن عمومی نشوند.

نسخه روی همان دیسک، برای آزمون restore مفید است؛ خرابی همان دیسک می‌تواند هم source و هم backup را از بین ببرد. برای محافظت مستقل، مقصد جدا و سیاست نگهداری لازم است؛ این تحویل آن‌ها را خودکار تنظیم نمی‌کند.

## تمرین

1. manifest یک دریافت failed را نشان می‌دهد. backup موفق، آن دریافت را موفق نمی‌کند؛ وضعیت تاریخی حفظ شده است.
2. پوشهٔ `.incomplete-backup-*` پس از خطای دیسک مانده است. بستهٔ موفق نیست؛ به‌عنوان backup معتبر استفاده نکنید.
3. restore به پوشهٔ موجود رد شده است. مقصد تازه بدهید؛ دادهٔ قبلی برای «جا بازکردن» حذف نشود.
4. تمام هش‌ها درست‌اند. حقیقت اقتصادی ناشر اثبات نشده؛ فقط سلامت بایت‌ها و سازگاری تعریف‌شده بررسی شده است.

کد مرتبط `backup.py`، `store_lock.py`، `Store.writer_lock` و `acquire` است. [روش تحویل](../source-methodology/store-recovery.fa.md) scope، کنترل‌ها و رفتار شکست را دقیق‌تر شرح می‌دهد.
